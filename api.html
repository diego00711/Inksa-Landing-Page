API para sistemas de loja

Como um PDV, ERP ou sistema de gestão recebe os pedidos feitos no Inksa, devolve o status e mantém o cardápio em dia — sem ninguém digitar duas vezes.

Versão 1.0 · Atualizada em 2 de setembro de 2026

Para quem é esta página

Para quem desenvolve o sistema que o restaurante já usa. O lojista não precisa ler nada aqui: ele gera uma chave dentro do aplicativo do parceiro e entrega para você.

O desenho é o mesmo que você já conhece de outras plataformas de delivery: o seu sistema pergunta ao Inksa se há pedido novo. Não precisamos de endereço público, porta aberta, IP fixo nem webhook do seu lado. Se o PDV da loja ficar sem internet por vinte minutos, nada se perde — na próxima pergunta os pedidos daquele período vêm juntos.

Começar em três passos

  1. O lojista gera a chave. No aplicativo do parceiro: Integração → Chaves de acesso → Gerar chave. A chave aparece uma única vez; ele copia e entrega para você.
  2. Você confere a chave chamando /status. A resposta diz de qual loja ela é. Se o nome não for o esperado, pare aqui.
  3. Você passa a perguntar por pedidos em /pedidos, a cada 30 ou 60 segundos.

Endereço e autenticação

https://inksa-auth-flask-dev.onrender.com/api/parceiro/v1

Toda chamada leva a chave no cabeçalho Authorization: 

Authorization: Bearer ink_live_xxxxxxxxxxxxxxxxxxxx

A chave vale para uma loja só. Rede com várias unidades usa uma chave por unidade. Tudo é JSON, em UTF-8.

A chave é uma senha. Guarde do lado servidor, nunca dentro do aplicativo instalado no caixa nem em código versionado. Se vazar, o lojista revoga na mesma tela em que gerou e o acesso cai na hora.

Conferir a chave

GET/status
# pedido
curl -H "Authorization: Bearer $CHAVE" \
  https://inksa-auth-flask-dev.onrender.com/api/parceiro/v1/status

# resposta
{
  "ok": true,
  "versao": "1.0",
  "ambiente": "live",
  "loja": {
    "id": "7a9057cb-cbcd-4c29-8799-65632b3ebd8d",
    "nome": "Yo!Frango frito e comida Coreana",
    "aberta": true
  },
  "servidor_em": "2026-09-02T23:39:51.265628+00:00"
}

Chame isto antes de qualquer outra coisa. É barato e evita o erro mais caro da integração: configurar a chave de uma loja no sistema de outra e só descobrir quando um pedido não chega — no movimento, com o cliente esperando.

Buscar pedidos

GET/pedidos?desde=<data ISO>&limite=<1..100>

Devolve os pedidos alterados depois de desde, do mais antigo para o mais novo. Sem desde, devolve as últimas 24 horas.

Guarde o proximo_desde da resposta e mande-o na chamada seguinte. Ele vem pronto justamente para você não precisar usar o relógio da sua máquina — se ele estiver alguns segundos adiantado em relação ao nosso, um pedido cai no vão e ninguém percebe. 
curl -H "Authorization: Bearer $CHAVE" \
  ".../pedidos?desde=2026-09-02T14:30:00Z"

{
  "pedidos": [ { /* ver formato abaixo */ } ],
  "quantidade": 1,
  "proximo_desde": "2026-09-02T14:52:07.113000+00:00"
}

O filtro é por última alteração, não por criação. Assim você recebe também o pedido antigo que mudou de estado — um cancelamento, por exemplo. Pedidos ainda aguardando pagamento e pedidos arquivados não aparecem.

Um pedido específico

GET/pedidos/<número>

O número é o mesmo que a loja vê na tela: 1001, 1002…

Formato do pedido

{
  "numero": 1001,
  "id": "65fea81c-b4c5-455f-ba5f-750516e574ff",
  "status": "pending",
  "criado_em": "2026-08-29T01:04:12.885694+00:00",
  "atualizado_em": "2026-08-30T00:41:38.268293+00:00",
  "pagamento": { "forma": "pix", "pago": true },
  "valores": { "itens": 79.87, "entrega": 5.0, "total": 79.87 },
  "entrega": {
    "tipo": "platform",
    "endereco": "Rua das Flores, 120 - Centro - Lages/SC — apto 302"
  },
  "cliente": { "nome": "Maria Oliveira", "telefone": "(49) 99999-0000" },
  "itens": [
    {
      "nome": "Trio Coreano Crocante (Individual) + refri",
      "quantidade": 1,
      "preco_unitario": 79.87,
      "observacao": null
    }
  ],
  "observacoes": ""
}
Não some itens + entrega esperando dar total. Quando há cupom, o cliente paga menos que a soma — o frete pode ter sido bancado pela plataforma, por exemplo. valores.total é o que o cliente pagou, e é esse o número que vale. A taxa de entrega não vem dentro da lista de itens: ela está só em valores.entrega, para a sua cozinha não imprimir "Taxa de Entrega" como se fosse um prato.

Em entrega.tipo, platform significa que um entregador do Inksa vai retirar; own significa que a própria loja entrega.

Mudar o status

POST/pedidos/<número>/aceitar
POST/pedidos/<número>/preparar
POST/pedidos/<número>/pronto

São os três passos da cozinha, nesta ordem:

pending  ──aceitar──▶  accepted  ──preparar──▶  preparing  ──pronto──▶  ready

aceitar aceita um corpo opcional com a previsão de preparo: 

curl -X POST -H "Authorization: Bearer $CHAVE" \
  -H "Content-Type: application/json" \
  -d '{"tempo_preparo_min": 25}' \
  .../pedidos/1001/aceitar

{ "ok": true, "numero": 1001, "status": "accepted" }
Repetir a mesma ação é seguro. Se você reenviar aceitar num pedido já aceito, a resposta é 200 com "observacao": "O pedido já estava neste status." — e não um erro. Isso existe porque tempo esgotado de rede acontece o tempo todo, e mostrar erro para o lojista num pedido que está certo é pior que o problema.

Chamar fora de ordem devolve 409 com o estado atual, para você decidir o que fazer: 

{
  "erro": "transicao_invalida",
  "mensagem": "Pedido #1001 está em 'ready'. 'aceitar' só vale quando está em 'pending'.",
  "status_atual": "ready"
}

Estados possíveis

StatusSignifica
pendingChegou. Esperando a loja aceitar.
acceptedA loja aceitou.
preparingEm preparo.
readyPronto. Libera a retirada.
accepted_by_deliveryUm entregador assumiu e está a caminho da loja.
deliveringSaiu para entrega.
deliveredEntregue.
cancelledCancelado.

Os quatro últimos você lê, mas não escreve — veja o porquê no fim da página.

Cardápio

GET/cardapio
POST/cardapio

O envio cria ou atualiza: pode mandar o cardápio inteiro quantas vezes quiser sem duplicar nada. A reconciliação usa o ean quando existe e, na falta dele, o nome do item dentro daquela loja. 

curl -X POST -H "Authorization: Bearer $CHAVE" \
  -H "Content-Type: application/json" \
  -d '{
    "teste": true,
    "itens": [
      {"nome":"Guaraná 2L","preco":"12,90","categoria":"Bebidas","ean":"7891234567890","estoque":40},
      {"nome":"Coxinha","preco":8.5,"categoria":"Salgados"}
    ]
  }' .../cardapio

{
  "ok": true, "teste": true,
  "recebidos": 2, "criados": 0, "atualizados": 0,
  "ignorados": [], "total_ignorados": 0
}
Rode com "teste": true primeiro. Valida tudo e não grava nada. A resposta lista, linha a linha, o que seria recusado e por quê — bem melhor que descobrir depois que trinta itens entraram sem preço.

preco aceita 12,90, 12.90, "R$ 12,90" e 1.234,56. Centavos como número inteiro não são aceitos, por ser ambíguo demais.

estoque é opcional. Zero não some do cardápio: o item fica visível e marcado como indisponível, porque o cliente precisa saber que a loja trabalha com aquele produto. Sem o campo, o item fica disponível.

Campo em branco não apaga o que já existe — em especial a descrição, que o lojista costuma caprichar no aplicativo e que quase nenhuma planilha de ERP carrega. Limite de 2.000 itens por chamada.

Erros

Todo erro devolve erro (código estável, para o seu switch) e mensagem (texto em português, que pode mudar). Trate pelo código, nunca pelo texto.

CódigoHTTPO que fazer
sem_credencial401Faltou o cabeçalho Authorization.
credencial_invalida401Chave errada ou revogada. Pare de tentar e avise o lojista.
nao_encontrado404O pedido não existe nesta loja.
transicao_invalida409Veja status_atual e siga dali.
parametro_invalido400Data fora do padrão ISO 8601, por exemplo.
sem_itens400Envio de cardápio sem a lista itens.
lote_grande400Mais de 2.000 itens. Divida em partes.
erro_interno500Problema nosso. Tente de novo em instantes.

Limites de chamada

RotaPor minuto
/pedidos e as ações de status120
/status60
GET /cardapio30
POST /cardapio10

Passando disso, a resposta é 429. Perguntar por pedidos a cada 30 segundos usa 2 das 120 chamadas — há folga de sobra, e não há motivo para perguntar de segundo em segundo.

O que a versão 1 não faz, e por quê

Duas coisas ficaram de fora de propósito, e não por falta de tempo:

Cancelar pedido. Cancelar um pedido já pago dispara o estorno ao cliente, e essa regra vive num único lugar do nosso sistema. Abrir um segundo caminho para devolver dinheiro é o tipo de duplicação que cedo ou tarde paga em dobro ou não paga. O lojista cancela pelo aplicativo.

Marcar "saiu para entrega" e "entregue". Essas duas passam por um código numérico conferido entre entregador, loja e cliente — é o que prova que a entrega aconteceu. Uma rota de API que pulasse o código permitiria fechar um pedido sem entregar nada.

Se a sua integração precisar de algo que não está aqui, fale com a gente. Esta versão continua no ar mesmo quando existir uma versão 2: quando o formato mudar, nasce /v2 e você migra quando puder. Nada quebra no meio do movimento.
